# core.py レビュー結果（Muse検証 → Geminiへの回答）

検証方法: Gemini の `core.py` をそのまま検証用ファイルに起こし、実物に近い
XMP サンプル（マスク付き／Crop有無／要素形式など）を作って
`_cleanse_xmp_for_raw` を実際に実行した。
検証コードとサンプルは `verify/` フォルダ（test_cleanse.py / samples/）にある。

## 結論

- 中心部分（Crop注入・座標変換の計算、マスク部分の保全）は合格
- ただし GUI 実装の前に、core 側で直してほしい点が下記 1〜3 ある
- 4〜6 は軽微な改善提案

## 合格した点（実地テスト済み）

- パターンA（未トリミング）: CropTop=0.055556 / CropBottom=0.944444 の
  注入が正しく行われ、XML として壊れていない
- パターンB（トリミング済み Top=0.1 / Bottom=0.9）:
  変換後 Top=0.144444 / Bottom=0.855556 で計算が正しい。
  CropAngle=3.5 もそのまま保持される
- `MaskGroupBasedCorrections` 部分はバイト単位で無傷。
  マスク名の日本語（線形グラデーション 1）も文字化けしない
- 抽出を `-xmp -b` のバイナリ方式にした判断は正しい

## 要修正 1: 画角を写真ごとに判定してほしい（最重要）

現行コードは「全写真が横位置・3:2撮影」を前提に定数を固定している。
以下のケースで誤動作する。

- 4:3 や 16:9、1:1 で撮った写真が混ざると、撮っていないはずの
  3:2 Crop が注入されてしまう（テスト G で再現）
- 縦位置写真では、カメラの 3:2 カットは上下ではなく左右を切るため、
  補正は CropTop/Bottom ではなく CropLeft/Right に必要になるはず

対策案: DNG ごとに `OriginalDefaultFinalSize` と RAW ネイティブ寸法を
ExifTool で読み、offset / scale を写真ごとに計算する。
寸法が一致する写真は補正をスキップする。縦横は DNG の
ImageWidth / ImageHeight の大小で判定する。
縦位置については、縦位置の実物サンプル 1 枚での確認も併せてお願いしたい。

## 要修正 2: 「何もしていないのに成功」になるケースをログ警告に

現行コードでは以下のケースで changes が空のまま成功扱いになる。

- `crs:HasCrop` 属性自体が無い XMP（テスト C で再現）
- Crop が要素形式 `<crs:CropTop>0.1</crs:CropTop>` の XMP（テスト D）
- CropTop だけある等、座標が片方欠けている XMP（テスト F）

実物の書き出し形式では起きない可能性はあるが、起きた時に無言で
成功になるのが一番危険。対象外形式だったら「未対応形式のため未処理」
とログに出して、成功枚数に数えないようにしてほしい。

## 要修正 3: 二重適用への備え

`_cleanse_xmp_for_raw` 自体は冪等ではない。変換済み XMP にもう一度
かけると座標がさらにズレる（テスト B2: Top 0.144444 → 0.183950）。
通常フローでは毎回 DNG から抽出し直すため再実行してもズレないが、
将来「既存 XMP を直接書き換える」使い方を足す場合は、
変換済みマーカー（独自属性等）で防いでほしい。現時点では
「DNG から抽出した直後の XMP 以外には適用しない」ことを
仕様として明記するだけでもよい。

## 改善提案 4: dc:format の要素形式に対応

`dc:format` が要素形式 `<dc:format>image/dng</dc:format>` の場合、
現行の正規表現では削除できない（テスト E で残存を確認）。
実物 EM1X7722.xmp の生テキストが属性形式か要素形式かを確認し、
要素形式なら削除処理を追加してほしい。
（tiff:ImageWidth 等の寸法タグも同様に要素形式の可能性がある）

## 改善提案 5: マスクの Y 座標の扱いを決める

マスク（線形グラデーション等）の ZeroY / FullY も JPG（3:2）基準の
座標のため、Crop だけ変換すると RAW 上で最大で約 5.6%
（画面端部）位置がズレる。
第1版では変換しなくてもよいが、その場合は「マスク使用時は位置が
少しズレる可能性がある」ことをログ警告に出すか、実写テストで
許容範囲かを確認してほしい。判断材料として残す。

## 改善提案 6: 細部（Windows 対策と GUI 連携）

- XMP の書き戻しは `write_text` ではなく `write_bytes` に。
  Windows では write_text が改行コードを CRLF に変換し、
  ファイル全体の改行が変わってしまうため
- 既存 XMP への配置は `shutil.move` ではなく `Path.replace()` に。
  Windows での上書きを確実にするため
- バックアップファイル名は拡張子 `.xmp` で終わらない形
  （例: `EM1X7722.xmp.bak_20261118_210000`）に。
  Lightroom がサイドカーとして誤認するのを避けるため
- `process_folder` に 1 ファイルごとの進捗コールバックと
  中断チェックを追加してほしい。現状は全件終わるまで GUI 側に
  何も返らないため、数百枚処理時に進捗表示と中止ができない
- `_resolve_exiftool` の探索順が docstring（指定パス優先）と
  実装（同階層優先）で逆になっている。どちらかに統一を

## GUI へ進むことについて

上記 1〜3 を core 側に反映できれば、PySide6 GUI へ進んで問題ない。
GUI 側では別スレッド実行＋進捗コールバック前提で設計してほしい。

## 追記（2026-11-18）: 要修正 1 の具体仕様

ポゴさんの実際の撮影内訳が判明したため、要修正 1 は「あれば直す」ではなく必須になった。

- 画角は 3:2 が多いが、縦位置が全体の約 1/3（横:縦 ≒ 2:1）
- 正方形（1:1）と横長（16:9）も時々使う

### 解き方: 定数をやめ、写真ごとに表示寸法の比から計算する

考え方は単純で、X軸・Y軸を別々に、まったく同じ式で処理する。

- その写真について、ExifTool で以下を読む
  - DNG 側: JPG の元寸法（`OriginalDefaultFinalSize`、無ければ
    `ImageWidth / ImageHeight` の比で代替）
  - ORF 側: RAW の寸法
  - 両方とも `Orientation` を見て、回転する写真は縦横を入れ替えた
    「表示寸法」に直してから使う
- 軸ごとに `scale = JPG表示寸法 / RAW表示寸法`、
  `offset = (1 - scale) / 2`（カメラの画角カットは中央基準のため）
- 変換: `CropLeft/Right` には X の offset・scale、
  `CropTop/Bottom` には Y の offset・scale を使う
  - `new = offset + old × scale`
- 未トリミング時の注入も同じ値で:
  `CropLeft=offset_x, CropRight=1-offset_x, CropTop=offset_y, CropBottom=1-offset_y`
  両軸とも offset がほぼ 0 の写真（4:3 ネイティブ撮影）は注入自体をスキップする

### この式で全ケースが自動で合うこと（数値検証済み）

- 横 3:2: Y のみ offset=0.055556 / scale=0.888889（現行の定数と一致）
- 縦 3:2: X のみ offset=0.055556 / scale=0.888889（左右が切れる）
- 横 1:1: X のみ offset=0.125 / scale=0.75
- 縦 1:1: Y のみ offset=0.125 / scale=0.75
- 横 16:9: Y のみ offset=0.125 / scale=0.75
- 縦 16:9: X のみ offset=0.125 / scale=0.75
- 4:3 ネイティブ: 両軸 offset=0 → 何もしない

### GUI 側への影響

- 「3:2 補正 ON/OFF」のチェックボックスは不要になる。
  代わりに「画角の自動補正（推奨・初期ON）」1つでよく、
  ポゴさんが写真ごとに画角を意識する必要はない
- ログには写真ごとに「横 3:2 と判定」「縦 1:1 と判定」のように、
  判定した画角と縦横を出すと、実機確認がしやすい
- 寸法が読めなかった写真は、補正をかけずに警告ログを出して
  通常のタグ掃除だけ行う（無言で定数をかけない）

### ついでに

マスク座標（ZeroX/FullX/ZeroY/FullY 等）も、同じ軸ごとの
offset・scale で変換できる形になる。第1版で入れるかは任意だが、
入れる場合の計算式は Crop と同一でよい。
